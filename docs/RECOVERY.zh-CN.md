## 你可以先这样运行

在仓库目录中使用 Python 3.10 以上版本：

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -e .
python -m srdrone demo --output runs/demo
python -m unittest discover -s srdrone/test -v
```

演示会走完“旧计划任务失败 → 分层反思 → 生成合法新计划 → 第二次执行 → 经验状态更新”。其中第一次行为树自身执行成功，但任务没有成功：无人机只到达框中心，没有飞到框另一侧。这对应论文强调的 plan-level failure。

演示中的模型输出和执行轨迹都是人工构造并明确标注的测试样例。它验证程序连接和状态转换；论文的成功率、解释准确率和真实飞行结果需要另外复现实验。

实际使用模型时，设置 `SRDRONE_API_KEY`、`SRDRONE_MODEL`，以及可选的 `SRDRONE_BASE_URL`，然后按英文 README 中的 `plan`、`evaluate`、`run` 示例运行。`evaluate` 会分析现有日志并导出候选行为树；`run` 才会等待执行器提供修正计划的新执行结果。模型调用会发送任务、场景和日志到你配置的服务，并把提示词与响应记录在本地运行目录。

## 核对中发现的关键差异

1. 原仓库的 evaluator/reflector 只返回占位输出，缺少实际模型推理与 XML 修正。
2. 旧 workflow 会把历史 BTlog 倒序取出作为下一轮；现在将历史分析和新计划重执行分开。
3. 笔记里同时存在 `SendPosition`、`FlyToCoordinates`、`FallBack`、`Fallback` 等不同版本写法，部分样例还有端口拼写错误或不支持的成员表达式。归档原文保持不动，运行协议以当前控制器实际接口为准。
4. 笔记中的 `ForwardDetectBalloon`、`DownScanHtag` 等节点没有在当前公开控制器中注册。不会仅凭节点名称假造感知实现；这些接口可以在后续找回传感器代码后扩展。
5. 控制器原来将执行路径固定为某台机器上的 `test.xml`，launch 中配置的路径没有被读取。本次改为私有参数读取，并给出明确的 launch 参数。
6. 原 TakeOff 节点缺少落盘的结束状态；Land 的历史 `finished` 日志也不能独立证明已经触地。新评估流程会保留原始测量和未知项，不会用理想轨迹覆盖它们。
7. README 原来写了 Apache-2.0，但缺少 LICENSE 文件；仓库中的 YOLOv5 源文件标有 GPL-3.0。本次补上项目许可证与第三方来源说明，保留各自归属。

## 恢复的边界

能够交付的是：有原文提示词依据、按照论文模块组织、可安装和可测试的重建版本。原始私有源码、完整 176 条失败评估数据、完整实验划分、baseline 改造代码、训练后的经验库、部分仿真资产和原实验运行记录，无法仅凭现有材料完整找回。

Python 闭环和安装包可以在当前机器验证。ROS1/Catkin、PX4/RflySim、MPNet 实际模型检索和真实飞行需要对应环境；当前交付不会把它们写成已完成验证。详细的方法对应关系见 [英文来源表](RECOVERY.md)，执行对接见 [EXECUTION.md](EXECUTION.md)，验证命令见 [VALIDATION.md](VALIDATION.md)。
